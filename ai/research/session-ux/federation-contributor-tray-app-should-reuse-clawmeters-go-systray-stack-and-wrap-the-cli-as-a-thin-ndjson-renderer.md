## CLAIMS

### Framework & distribution
- Clawmeter (the cited "clawmeter-style" bar) is Go and uses only `fyne.io/systray` (tray-icon lib, a `getlantern/systray` descendant), `gen2brain/beeep` (native notifications), and `pkg/browser` (`OpenURL` for OAuth) — NOT the full fyne GUI/widget toolkit; it has no windows/widgets, its "modals" are OS notifications + the tray menu [clawmeter-repo].
- The required surface for a Federation contributor GUI (tray icon, shell out to a CLI, parse JSON stdout, occasional native notification, browser-open for OAuth) is exactly clawmeter's existing surface — no capability gap that Tauri/Electron/Wails would close [clawmeter-repo].
- Verdict: build in Go + `fyne.io/systray` (reuse clawmeter's fork), ranked #1; Wails #2 (only if richer in-app windows become required, stays in Go); Tauri #3; Electron #4 (last resort). A second toolchain is pure added cost for a solo dev given the tiny surface [clawmeter-repo].
- Electron is over-weight for a tray+notifications surface: installers 50-150MB+, 100-300MB idle RAM; Ollama's Electron tray has documented friction (no dock icon, "not responding" ghost state, unclean quit) despite the heavier stack [ollama-app-arch].
- Distribution reuses clawmeter's pipeline near-unchanged: Homebrew formula building from source (sidesteps macOS notarization), `.app` bundle with `LSUIElement=true` (no Dock icon), `brew services` for the one-line start, XDG `~/.config/autostart/*.desktop` for Linux autostart, existing `.deb`/`.rpm`/winget artifacts [clawmeter-repo].
- Unavoidable Linux caveat (inherited, not introduced): GNOME 45/46 ship no native StatusNotifierItem/AppIndicator; the tray icon requires a GNOME Shell extension (AppIndicator support / Tray Icons Reloaded). Document it; not fixable app-side. Modern KDE works out of the box [gnome-appindicator, clawmeter-repo].

### Contributor UX patterns
- The most non-technical-friendly volunteer-compute apps (Honeygain, Salad, Folding@home) share: (a) one big obvious toggle/status not a settings panel, (b) proactive short notifications when attention is needed rather than a dashboard the user must check, (c) honest hedged numbers for contribution/credit, not precise-looking-but-fake stats [honeygain, salad, folding-at-home].
- Tray icon should have exactly 3 states: contributing (normal), paused (user-initiated), action-needed (badge/notification) — distinct glyphs; do NOT fold "needs login" into a generic "offline/disconnected" state (Nextcloud's bug history shows that ambiguity confuses users) [salad, nextcloud-tray-issues].
- Docker Sandboxes' security docs are the reusable trust/safety copy template: a 3-part structure — one-sentence boundary claim → short "shared-in / not-touched" list pair → one explicit negative-space sentence ("everything else is blocked: cannot read your other files, cannot reach your home network, cannot see other tasks") [docker-sandboxes-security]. Honeygain's "only X, never Y" contrast + "pause anytime, nothing runs while paused" control line reinforce it for non-technical users [honeygain].
- Infrastructure-grade products (BOINC signed account-manager URLs, Storj/Render node reputation scores) show a visible trust/reputation signal matters even to end users — surface the coordinator/peer `trusted{key_id}` state as a simple "Coordinator: trusted" badge [boinc-simpleattach, storj-node-dashboard].
- Join-by-invite best pattern: a single paste field that accepts a deep link (`waspflow://join?coordinator=...&token=...`), a full `join <url> <token>` command, or a raw token, auto-detecting which; then a single confirm screen showing the parsed coordinator URL for sanity-check before committing. Pre-fill everything; no project-picker/config screen (BOINC's SimpleAttach collapsed a many-click flow to one "Join") [boinc-simpleattach].

### Auth-handoff
- For the clickable-URL case (`awaiting_browser{url}`, e.g. Codex OAuth), use the GitHub-CLI device-flow shape: tray state flips on the event, a native notification with an "open URL" action fires, the action stays available in the menu even if the toast is dismissed (persistent, not one-shot), the underlying CLI process polls in the background, and the tray auto-clears on completion (no "you're done!" modal) [github-cli-device-flow].
- For the irreducibly-manual case (`auth_required_manual{instruction}`, Claude subscription `/login` inside a sandbox — no host-side URL exists), render the `instruction` text as a plain numbered card (NOT a fake button), state explicitly it is a one-time unavoidable manual step and why, and badge the tray with the SAME "action-needed" urgency as the URL case [github-cli-device-flow, docker-sandboxes-security].

### CLI↔GUI integration architecture
- The shipped `bin/waspflow-federation --json` emits one terminal JSON line per invocation (via a single `printResult(json, humanLines, structured)` helper) and streams live progress on stderr; events include `joined/already_joined/not_joined`, `auth_required_manual{harness,flow_shape,instruction}`, `awaiting_browser{harness,url}`, `no_task_available`, `contributed{task_digest}`, `trusted{key_id}`, `task_status` [waspflow-fedv0-ux-branch].
- For v0, spawn-per-command with NDJSON-over-stdout parsing is correct (matches lazygit/gitui/gh's "thin renderer, real logic in the binary"); the CLI is invocation-shaped (two main verbs), not session-shaped, so no daemon is needed [lazygit-gitui, github-cli-device-flow, node-child-process].
- Treat stderr as opaque progress text only; never parse it for control flow — only the stdout JSON lines are the contract (the Docker lesson: CLI-as-thin-client works only if the events, not the human text, are the source of truth) [docker-daemon, flamenco].
- GitHub Desktop vs `gh` is the anti-pattern: two fully independent reimplementations (Electron/TS vs Go) sharing no runtime relationship, which drift into duplicate divergent logic — validates keeping the GUI as a renderer over the one CLI, so one security review covers both surfaces [github-desktop-vs-gh].
- Contract discipline to add before a GUI depends on it: a `schema_version` field per emitted event line (the shipped events carry none yet) so the GUI can detect+degrade on unknown events; a single shared schema/type as source of truth imported by both emitter and parser; CI golden-output tests validating real `--json` runs against that schema. JSON schemas have "no such thing as a bug fix" so version explicitly (cf. SchemaVer) [syncthing-events-api, snowplow-schemaver].
- Graduate to a daemon + event-endpoint (Syncthing long-poll `/rest/events?since=` with monotonic ids + heartbeat, or Ollama/Docker-Desktop's supervised-daemon+API model) ONLY when you need multiple simultaneous observers, state that survives a GUI crash without re-invoking the operation, or a long-running `contribute --loop` — none true of v0 [syncthing-events-api, ollama-app-arch, docker-daemon].

### Requester/submit side
- Render-farm/notebook-job submitters are the closest prior art for "submit a job, watch it, get output back": keep the submit surface thin (Flamenco/Deadline separate the submit form from the monitor view) [flamenco, aws-deadline].
- Recommended submit UX: a 3-field form (native folder picker → `--source`, plain multiline prompt box → `--prompt-file`, display-id field), a single horizontal stepper for the lifecycle (`queued → claimed → running → settled`) updated by polling `status --json`, each transition also a toast, and — critically — a SEPARATE "result branch ready" affordance decoupled from "settled" (SageMaker's "output available" indicator lights independently of job success, because a failed/partial run may still have a branch worth reviewing, matching v0's review-like-a-PR model) [flamenco, aws-deadline, sagemaker-notebook-jobs].
- Coarse states beat executor internals for the watcher (Deadline worker states are just Idle/Rendering/Stalled) [aws-deadline].

## CORRECTION (2026-07-21, same day) — the STACK conclusion was FLIPPED by an end-state pressure-test

The title/framework verdict below ("reuse clawmeter's Go + fyne.io/systray") was the right answer to the NARROW question "cheapest tray app matching clawmeter's UX bar" but the WRONG answer to "what stack fits waspflow's product end state." A follow-up decision memo (owner-prompted: "not 100% sure Go is the best fit for the ideal end state") established, with verified repo facts:
- The federation surface is 1,389 lines across 6 Node.js binaries, last touched the same day, actively growing across worktrees; the bash core (~6k lines) is stable/frozen (last touched 2026-07-16); a root `package.json` (node>=20) already exists. **Node is waspflow's growing product surface.**
- A Go GUI would be a THIRD language whose only job is re-parsing JSON a Node process emits natively — a cross-language IPC seam + second toolchain for a solo maintainer. The first pass costed "Go isn't a new toolchain" against Go-*clawmeter*, not against the Node-*CLI it wraps*; against the correct baseline, Go IS the second toolchain.
- Language-split GUIs carry documented friction (Ollama Go-daemon+Electron; gh vs GitHub-Desktop = divergent reimplementations); consolidated success cases share a language family (Tailscale all-Go; 1Password killed a 2nd native GUI to avoid the churn).
- Systray-only libs (Go's fyne.io/systray OR Node's systray2) have NO window capability; the join screen + submit form force a real webview/windowing toolkit regardless — so the real choice is Tauri/Electron (Node family) vs Wails (Go family), not systray-vs-systray2.

**FINAL VERDICT (after two more research passes — install-ease, then web-UI-vs-native): a HYBRID, not a native GUI at all.**
- **Rich screens (join, trust panel, requester submit+watch) → a localhost WEB UI** served by a Node daemon and opened in the user's OWN browser. No bundled webview → the Linux webkit2gtk "won't launch" hazard vanishes; no `.app`/`.exe` GUI → most macOS-notarization / Windows-SmartScreen burden vanishes; most apt-repo-friendly shape (daemon + systemd unit, no `.desktop`/icon/webview deps — the Syncthing/Jellyfin/Cockpit model).
- **A native TRAY is REQUIRED (owner, non-negotiable)** for the ambient contributing/needs-attention signal — but MINIMAL: 2-3 states + a menu that OPENS the web UI URL and auto-opens on auth-needed. It renders none of the rich UI.
- **The thin tray → Go + fyne.io/systray (clawmeter's ACTUAL stack) becomes correct again**, because a tray-that-opens-a-URL needs NO webview (clawmeter's binary links only libc-level libs, zero webkit). The earlier "systray-only can't do windows so we need Tauri/Electron/Wails" reasoning only held while the tray had to render the rich screens; it doesn't once those are in the browser. The Node/Go split is fine here: the tray shares ZERO logic with the daemon (polls state, opens a URL) — nothing to hand-port, unlike a full native GUI.
- **Install/distribution:** apt (own signed repo, reprepro/aptly, Syncthing's `signed-by=` pattern) + brew + WinGet/Scoop; daemon depends on `nodejs`; tray is a tiny libc-only binary; systemd `--user` / launchd / XDG-autostart for persistence. `syncthingtray` (mainline Debian, WinGet, no signed installer) is the direct packaging template.
- **Localhost security (must-build, standard):** bind 127.0.0.1, validate Host header (DNS-rebinding defense — cf. Ollama CVE-2024-28224, MCP SDK CVE-2025-66414), require a local token (not IP-trust), no wildcard CORS. Syncthing proves the pattern.
- **Honest scope correction:** the existing `lib/federation-coordinator.mjs` node:http server is the OWNER-HOSTED machine-to-machine JSON coordinator API (serves zero HTML) — NOT a local contributor UI. The contributor-side local web UI is a NEW daemon to build (same runtime/idiom as the coordinator — a well-understood build, not a new capability class).

Everything language-independent in the sections below stands (thin-renderer-over-the-loop, schema_version+golden-test contract, 3-state tray, device-flow auth-handoff, Docker-Sandboxes trust copy, decoupled result-ready). SUPERSEDED intermediate picks: Go-clawmeter-GUI (too narrow) and Node/Tauri-native-GUI (install-ease + apt tipped it to web-UI+thin-tray). Decision doc: `waspflow/docs/design/FEDERATION_GUI_DESIGN.md` (ARCHITECTURE section).

## SYNTHESIS

Three independent research passes converged with no conflicts on the UX/architecture, which raises confidence in everything EXCEPT the stack pick (see CORRECTION above — the stack flipped to Node/Tauri once judged against waspflow's end state rather than against clawmeter). The original text below is retained for the record: build the Federation contributor GUI in ~~Go + fyne.io/systray, reusing clawmeter's exact stack~~ [SUPERSEDED → Node/TS + Tauri-sidecar] and its entire brew/`.app`/autostart/`.deb`/`.rpm` distribution pipeline — a sibling app in the same family, not a new toolchain. Architect it as a **thin spawn-per-command NDJSON renderer** over the already-shipped `waspflow federation` CLI (the loop's logic and security stay in the one binary; the GUI reimplements nothing — GitHub-Desktop-vs-gh is the cautionary anti-pattern). The CLI's structured events already map 1:1 onto the UI: a **3-state tray icon** (contributing / paused / action-needed), a **paste-one-field join** (deep link / command / token, auto-detected), a **device-flow auth-handoff** for `awaiting_browser{url}` and an **honest numbered-instruction card** for `auth_required_manual` (same urgency badge, different remediation), Docker-Sandboxes-style **3-part safety copy** plus a `trusted{key_id}` **"Coordinator: trusted" badge**, and a requester **submit form → horizontal lifecycle stepper → decoupled "result ready" affordance**. The one cheap thing to do to the CLI *before* the GUI depends on it: add a `schema_version` field to the single `printResult` emitter and a golden-output CI test, so the event contract is versioned and drift is caught at build time. Defer any daemon/event-endpoint until multi-observer or restart-durable state is actually needed.
