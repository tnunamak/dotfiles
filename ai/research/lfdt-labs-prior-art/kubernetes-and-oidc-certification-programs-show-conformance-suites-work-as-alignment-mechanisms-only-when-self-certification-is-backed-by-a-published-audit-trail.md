## CLAIMS

### Kubernetes: KEP process, API deprecation policy, conformance program

- The Kubernetes Enhancement Proposal (KEP) template formally ties API graduation to test coverage via an explicit, checked release-signoff requirement: "(R) all GA Endpoints must be hit by Conformance Tests within one minor version of promotion to GA." [k8s-kep-template-conformance-rule]
- The same KEP template requires a test plan to exist before a feature can even target a milestone ("(R) Test plan is in place"), requires "e2e Tests for all Beta API Operations (endpoints)," and requires GA promotion to be preceded by "(R) Minimum Two Week Window for GA e2e tests to prove flake free" — i.e., graduation between maturity stages is gated by concrete, checked testing artifacts, not just design review. [k8s-kep-template-conformance-rule]
- Kubernetes' official API deprecation policy sets exact, numeric alignment windows per maturity level rather than leaving timing to project discretion: "GA API versions may be marked as deprecated, but must not be removed within a major version of Kubernetes"; "Beta API versions are deprecated no more than 9 months or 3 minor releases after introduction (whichever is longer), and are no longer served 9 months or 3 minor releases after deprecation (whichever is longer)"; "Alpha API versions may be removed in any release without prior deprecation notice." [k8s-deprecation-policy]
- The stated rationale for the beta-API timeline ties it directly to a separate, numeric compatibility guarantee (version skew support): "This ensures beta API support covers the maximum supported version skew of 2 releases, and that APIs don't stagnate on unstable beta versions, accumulating production usage that will be disrupted when support for the beta API ends." [k8s-deprecation-policy]
- The Certified Kubernetes Conformance Program uses an open-source test tool (Sonobuoy) that any party — vendor or end user — can run identically: "Any end user can confirm that their distribution or platform remains conformant by running the identical open source conformance application (Sonobuoy) that was used to certify." [k8s-conformance-program]
- Certification is self-certified with a publicly reviewable submission, not a third-party audit: a vendor runs the conformance suite, then must "prepare a PR to submit your results to the Conformance repo on GitHub," after which a CNCF reviewer "approve[s] your PR at which point you are certified" — the trust mechanism is public review of a submitted PR, not an independent auditor visiting the vendor. [k8s-conformance-program]

### OpenID Foundation OIDC Certification

- OIDC certification tests are run using conformance-testing software built and hosted by the OpenID Foundation itself, described as "the free suite of conformance tests," available to any implementer at certification.openid.net, and the Foundation states plainly that certification is evaluating "how well their products and implementations conform to our most mature, stable standards." [oidc-certification-page]
- Certification is currently a self-certification model: implementers run the Foundation's own conformance tests against their implementation and "follow a self-certification process" — there is no mandatory independent auditor in the loop today. [oidc-certification-page]
- The OpenID Foundation is actively building out third-party oversight as a planned addition to (not yet a replacement for) self-certification, signaled by its own forward-looking language: "This page will be updated as those services mature," referring to third-party auditors/testing-service providers still in development at time of review. [oidc-certification-page]

### Terraform BSL relicensing and the OpenTofu fork — a live governance-rupture case study

- On August 10, 2023, HashiCorp announced it was relicensing all future releases of Terraform (and Vault, Consul, Nomad) from the Mozilla Public License v2.0 to the Business Source License v1.1, with Terraform v1.5.7 and all earlier releases remaining under MPL v2.0. [terraform-bsl-announcement-search]
- HashiCorp's stated reasoning was explicitly aimed at commercial competitors building on its open-source work, not at end users: the change would "allow us to continue investing in our community while ensuring our competitors cannot take advantage of our open source work," and going forward HashiCorp began calling its freely-available builds "community editions" rather than "open source," since BSL does not meet the OSI's open-source definition. [terraform-bsl-announcement-search]
- Community response escalated on a fast, concrete timeline: the "OpenTF Manifesto" calling for reversal was published August 15, 2023 (five days after the announcement); the manifesto crossed 32,000 GitHub stars; a fork ("OpenTF") went public by August 25, 2023; and the Linux Foundation accepted the fork as a hosted project on September 20, 2023, at which point it was renamed OpenTofu. [terraform-bsl-announcement-search] [opentofu-launch-announcement]
- OpenTofu's Linux Foundation launch already had substantial committed engineering capacity at day one — "over 18 full-time equivalents (FTEs) committed to the project from four companies," with the founding manifesto endorsed by more than 140 companies and roughly 700 individual participants across 11 related projects — a materially larger and faster-mobilized founding coalition than any other fork precedent surveyed in this corpus. [opentofu-launch-announcement]
- OpenTofu reached its first stable, production-ready release (v1.6, "general availability") on January 10, 2024 — under five months after the BSL announcement that triggered the fork. [opentofu-launch-announcement]
- OpenTofu was accepted into the CNCF (a further, deeper neutral-foundation step beyond the initial Linux Foundation hosting) in April 2025. [opentofu-launch-announcement]
- The rupture was not purely a one-time licensing event — it recurred as a direct legal conflict roughly eight months later: in April 2024, HashiCorp sent OpenTofu a cease-and-desist notice alleging OpenTofu had incorporated code originating from a BUSL-licensed version of Terraform without permission; OpenTofu denied the allegation, countering that the cited code originated from an MPL-licensed version predating the relicensing. [opentofu-cease-desist]
- Despite the governance/license rupture at the CORE level, the provider ECOSYSTEM did not fragment at the wire-protocol level: OpenTofu deliberately kept the same provider plugin protocol, so "any tool that hosts Terraform providers also hosts OpenTofu providers" and most existing tooling (Terraform Cloud/HCP Terraform, Spacelift, Scalr, env0, JFrog Artifactory, GitLab's built-in registry) works with OpenTofu providers unmodified. [opentofu-registry-mechanics]
- OpenTofu did stand up its own separate provider registry (`registry.opentofu.org`, distinct from HashiCorp's `registry.terraform.io`) hosting most major providers (including HashiCorp-maintained ones like AWS, AzureRM, Google), but explicitly supports cross-registry sourcing — a provider's source address can name `registry.terraform.io` directly for providers not mirrored into the OpenTofu registry, meaning the fork did not force a hard, exclusive choice on provider authors. [opentofu-registry-mechanics]
- OpenTofu built a "Provider Network Mirror Protocol" specifically to manage residual fragmentation risk — an optional protocol letting a self-hosted internal server "serve providers belonging to any registry hostname" (both `registry.opentofu.org` and `registry.terraform.io` sources) from one place, so an organization does not need to depend on either public registry's uptime or policies to consume providers from both ecosystems. [opentofu-registry-mechanics]
- A provider-signing/trust distinction persists between the two ecosystems even where sourcing is shared: HashiCorp-signed providers retain their original HashiCorp signature and are verified as such when downloaded through OpenTofu tooling, while community-maintained providers hosted in the OpenTofu registry are instead signed with a separate OpenTofu signing key — i.e., trust roots did fragment even though sourcing/hosting did not. [opentofu-registry-mechanics]
- The Terraform plugin protocol is an explicitly versioned gRPC/Protocol-Buffers interface between core and providers, with major-version boundaries marking compatibility breaks and minor versions being additive-only; protocol v5 supports "Terraform CLI version 0.12 and later," while protocol v6 supports "Terraform CLI version 1.0 and later" and is described as maintaining backward compatibility with v5 functionality while adding Nested Attributes support (structured nested schema fields with independent per-field sensitivity marking) as its core new capability. [terraform-plugin-protocol-versions]
- Protocol-version compatibility between a given Terraform/OpenTofu CLI release and a given provider release is negotiated/discovered through registry metadata rather than a live runtime handshake alone: "the Terraform Registry uses the protocol version as additional compatibility metadata when deciding which plugin versions Terraform CLI can select," with that metadata declared by the provider author in the registry manifest at release time. [terraform-plugin-protocol-versions]
- HashiCorp provides explicit migration tooling (`tf5to6server` to upgrade a v5 provider to speak v6, `tf6muxserver` to combine multiple v6 providers behind one binary) rather than forcing an abrupt cutover — the SDKv2-to-plugin-framework and protocol v5-to-v6 transitions are both designed as optional, tool-assisted migrations a provider author can defer indefinitely rather than a forced deprecation with a hard removal date (no removal date for v5 or SDKv2 was found in this research). [terraform-plugin-protocol-versions]

## SYNTHESIS

Kubernetes and OIDC certification converge on the SAME model — self-certification against a shared, open-source test suite, made trustworthy by public reviewability rather than a paid third-party auditor — and this is directly good news for PDP-Connect, because it means the credible version of "compat matrix enforced by a conformance suite + certification mark" does NOT require standing up an expensive audit apparatus. Kubernetes' mechanism (run Sonobuoy, submit a PR with results to a public GitHub repo, a reviewer approves it) and OIDC's mechanism (run the Foundation's own free conformance suite, self-certify) are both cheap to operate and both derive their credibility from the test suite and the results being public and re-runnable by anyone — not from who ran it. For PDP-Connect, a `data-connectors`-wide (or `data-connect`-wide) "PDPP Conformant" mark could copy this exactly: publish an open-source conformance test suite as part of `pdpp` or a sibling repo, require a PR with published results to claim the mark, and let anyone re-run the suite to check a claim — no auditor budget required. Note the honest caveat: the OpenID Foundation itself says third-party oversight is still being built out as an ADDITION to self-certification, which suggests even a mature 15+-year-old standards body sees self-certification-alone as a stage to grow beyond eventually, not a permanently sufficient end state — PDP-Connect should expect to revisit this as the ecosystem matures, not treat self-certification as forever-adequate.

Kubernetes' API deprecation policy is the single most directly copyable artifact in this whole research effort: EXACT numeric windows (9 months or 3 minor releases, whichever is longer, for both the deprecation warning period and the actual removal), explicitly derived from a separate numeric compatibility guarantee (2-release version skew support). This is more concrete than anything else surveyed across OTel, GraphQL, Matrix, or atproto — those all describe compatibility qualitatively ("must not create version conflicts," "must be bidirectionally valid") rather than with a release-count number. PDP-Connect should pick actual numbers for `pdpp` field/capability deprecation (e.g., "a deprecated PDPP field remains valid for N `data-connect` minor releases or M months, whichever is longer") rather than leaving deprecation timing to case-by-case judgment — Kubernetes' 15+ years of running this exact numeric policy at enormous scale is strong evidence it works.

The Terraform/OpenTofu situation is the cautionary tale PDP-Connect explicitly asked about, and the actual lesson is more specific and more useful than "license changes are bad": the provider ECOSYSTEM survived the core's unilateral governance/license rupture reasonably intact specifically BECAUSE the wire protocol (the versioned gRPC provider plugin protocol) stayed a shared, backward-compatible artifact that neither side had reason to break — OpenTofu didn't need to reinvent it, and HashiCorp had no technical reason to change it just to spite the fork. What DID fragment was everything ABOVE the wire protocol that depends on institutional trust: the package registry (two separate registries now exist, requiring explicit cross-sourcing configuration to bridge), and the signing/trust root (OpenTofu had to mint its own signing key for community providers, permanently forking trust even where hosting didn't fork). The direct lesson for PDP-Connect's `data-connectors` design: invest disproportionately in making the wire-level contract between `data-connect` and connectors (the actual data shapes / RPC surface, not the registry or trust infrastructure around it) something that would keep working even in a worst-case governance rupture between Vana and a neutral steward — because that is the layer this real-world precedent shows actually survives a fork, while registry/trust infrastructure is the layer that predictably duplicates. The April 2024 cease-and-desist episode (flagged here as sourced from secondary reporting, not independently verified against a primary legal document) is a reminder that a single relicensing announcement is not necessarily the end of the conflict — a genuinely adversarial fork can recur as ongoing IP disputes for years afterward, which argues for PDP-Connect getting IP/licensing boundaries between `pdpp`, `data-connect`, and Vana's own products unambiguous from day one rather than deferring that clarity, precisely to avoid ever being in HashiCorp's position of alleging code-provenance violations against a project it does not control.
