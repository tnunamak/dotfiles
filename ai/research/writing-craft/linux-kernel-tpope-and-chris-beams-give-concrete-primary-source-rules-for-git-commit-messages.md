## CLAIMS

- The Linux kernel's `Documentation/process/submitting-patches.rst`, in its "Describe your changes" section, requires four specific things in a patch/commit body: (1) describe the underlying problem that motivated the work — "there must be an underlying problem that motivated you to do this work," (2) describe user-visible impact with concrete evidence ("provoking circumstances, excerpts from dmesg, crash descriptions, performance regressions, latency spikes, lockups, etc."), (3) quantify optimizations/trade-offs with numbers if performance is claimed, and (4) only then describe the technical solution "in plain English for the reviewer to verify that the code is behaving as you intend it to." [kernel-submitting-patches]
- The kernel doc frames the problem description as reviewer-persuasion, not just record-keeping: "Convince the reviewer that there is a problem worth fixing and that it makes sense for them to read past the first paragraph." [kernel-submitting-patches]
- The kernel doc does NOT contain an explicit instruction to describe alternative approaches considered or rejected — this specific claim (sometimes attributed to kernel convention in secondary sources) does not appear verbatim in the current "Describe your changes" section of `submitting-patches.rst`. The closest adjacent language is "include the complete patch description and justification for it" when resubmitting. [kernel-submitting-patches]
- The kernel doc separately mandates imperative mood, with kernel-specific phrasing distinct from tpope's/Beams's: "Describe your changes in imperative mood, e.g. 'make xyzzy do frotz' instead of '[This patch] makes xyzzy do frotz' or '[I] changed xyzzy to do frotz', as if you are giving orders to the codebase to change its behaviour." [kernel-submitting-patches]
- The kernel doc requires "Solve only one problem per patch," justified by reviewability: "If your description starts to get long, that's a sign that you probably need to split up your patch." [kernel-submitting-patches]
- Tim Pope's 19 Apr 2008 post "A Note About Git Commit Messages" (tbaggery.com — not chris.beams.io/tpope.net, which are secondary/broken mirrors) gives the original model commit format: a "Capitalized, short (50 chars or less) summary," followed by a blank line, then a body "wrap[ped]... to about 72 characters or so." [tpope-tbaggery]
- Tpope's stated rationale for the blank line separating subject from body is tool compatibility, not readability: "The blank line separating the summary from the body is critical (unless you omit the body entirely); tools like rebase can get confused if you run the two together." [tpope-tbaggery]
- Tpope's stated rationale for imperative mood is consistency with Git's own auto-generated messages: "Write your commit message in the imperative: 'Fix bug' and not 'Fixed bug' or 'Fixes bug.' This convention matches up with commit messages generated by commands like git merge and git revert." [tpope-tbaggery]
- Tpope's stated rationale for the 72-character body wrap is twofold and mechanical, not aesthetic: (1) `git log`'s default pager (`less -S`) does no special wrapping, so on an 80-column terminal, subtracting 4 columns of left indent and 4 for right-side symmetry leaves 72; (2) `git format-patch --stdout` turns commits into plain-text emails, and email netiquette requires room for a few levels of nested reply-quote indicators (`>`) without overflowing 80 columns. [tpope-tbaggery]
- Tpope explicitly says 50 characters "isn't a hard maximum," and lists eight concrete places in Git tooling where the subject line surfaces (often truncated if too long): `git log --pretty=oneline`, `git rebase --interactive`, `merge.summary` config, `git shortlog`, `git format-patch`/`git send-email`, `git reflog`, `gitk`, and GitHub's UI. [tpope-tbaggery]
- Chris Beams's "How to Write a Git Commit Message" (originally chris.beams.io/posts/git-commit/, 31 Aug 2014; chris.beams.io now 301-redirects to the canonical current URL cbea.ms/git-commit/) states the seven rules verbatim as: (1) Separate subject from body with a blank line, (2) Limit the subject line to 50 characters, (3) Capitalize the subject line, (4) Do not end the subject line with a period, (5) Use the imperative mood in the subject line, (6) Wrap the body at 72 characters, (7) Use the body to explain what and why vs. how. [chris-beams-cbea]
- Beams explicitly frames these seven rules as not his own invention but a distillation of prior, already-established convention: "Keep in mind: This has all been said before." He names the Linux kernel, Git itself, Spring Boot, and "any repository managed by Tim Pope" as pre-existing exemplars of the style before stating the rules. [chris-beams-cbea]
- For rule 1, Beams quotes the `git commit` manpage's DISCUSSION section directly as the authoritative source: "Though not required, it's a good idea to begin the commit message with a single short (less than 50 character) line summarizing the change, followed by a blank line and then a more thorough description. The text up to the first blank line in a commit message is treated as the commit title, and that title is used throughout Git." [chris-beams-cbea]
- For rule 2, Beams's stated rationale is cognitive, not just mechanical: the 50-char limit "ensures that they are readable, and forces the author to think for a moment about the most concise way to explain what's going on," and notes GitHub's UI enforces this — warning past 50 chars, truncating with an ellipsis past 72. His summary heuristic: "shoot for 50 characters, but consider 72 the hard limit." [chris-beams-cbea]
- For rule 5 (imperative mood), Beams gives a different justification than tpope's "matches Git's own commands" framing — he adds a testable heuristic: "A properly formed Git commit subject line should always be able to complete the following sentence: If applied, this commit will <your subject line here>." He shows this test fails for indicative-mood subjects like "Fixed bug with Y" or "More fixes for broken stuff." [chris-beams-cbea]
- For rule 6, Beams's rationale matches tpope's mechanical framing but restates it independently: wrapping at 72 "so that Git has plenty of room to indent text while still keeping everything under 80 characters overall." [chris-beams-cbea]
- For rule 7, Beams's core "why not what" argument is explicitly credited to a third party, not original to him: "A diff will tell you what changed, but only the commit message can properly tell you why. Peter Hutterer makes this point well: Re-establishing the context of a piece of code is wasteful... a commit message shows whether a developer is a good collaborator." [chris-beams-cbea]
- Beams's rule-7 guidance draws an explicit three-way distinction — what / why / how — and assigns "how" to the code itself, not the commit message: "In most cases, you can leave out details about how a change has been made. Code is generally self-explanatory in this regard (and if the code is so complex that it needs to be explained in prose, that's what source comments are for). Just focus on making clear the reasons why you made the change in the first place—the way things worked before the change (and what was wrong with that), the way they work now, and why you decided to solve it the way you did." [chris-beams-cbea]
- Beams's worked example for rule 7 is a real Bitcoin Core commit (`eb0b56b`, Pieter Wuille, "Simplify serialize.h's exception handling") whose body explains the prior broken state, the mechanism of the fix, and the downstream consequence (`good()` never reached after failure) — used as a positive exemplar of "what and why" without restating "how" line-by-line. [chris-beams-cbea]

## SYNTHESIS

These are three genuinely independent primary sources, not one convention with three retellings — worth keeping separate because they disagree in emphasis and one popular attribution doesn't hold up. The kernel doc is process-first: it cares about persuading a reviewer that a problem exists and is worth fixing, and about routing fixes downstream to stable trees (hence "provoking circumstances, excerpts from dmesg"). It has no 50/72 rule at all — that's purely a tpope/Beams convention, not a kernel one. And contrary to a claim sometimes folded into "kernel commit-message wisdom," the current `submitting-patches.rst` does not explicitly ask authors to describe alternatives considered and rejected — that's closer to the ethos of good design docs / RFCs than to this specific document's actual text. Don't repeat that attribution without a second check against a different kernel doc (e.g. `development-process.rst`) if it matters later.

Tpope's post is narrower and more mechanical than its reputation suggests: it's really just the 50/72 formatting convention plus imperative mood, justified almost entirely by tool compatibility (`rebase`, `git log`'s non-wrapping pager, `format-patch`'s email conversion) — there's no "why not what" content guidance in the original 2008 post at all. That guidance is Beams's addition six years later (rule 7), which he explicitly credits to Peter Hutterer's framing, not to tpope. The common shorthand "tpope's 50/72 rule" is accurate for the numbers but attributing the "explain why not what" doctrine to tpope is a conflation — check this before citing it that way.

Beams's essay is the one that actually synthesizes into "seven rules," and he's explicit that he's distilling pre-existing convention, not inventing it — he names the kernel, Git itself, and tpope's repos as prior art before stating rule 1. His real original contributions are (a) the "if applied, this commit will ___" testable heuristic for imperative mood, which neither the kernel doc nor tpope's post has, and (b) the explicit what/why/how three-way split with "how belongs in code comments, not the commit message" — sharper than tpope's version, which doesn't address "how" as a category at all.

One live-link gotcha worth recording since it will bite anyone following an old citation: `chris.beams.io/posts/git-commit/` now 301-redirects to `cbea.ms/git-commit/` (domain change), and the tpope.net mirror Beams's page links to is broken (TLS cert mismatch / 404) — the actual working original is `tbaggery.com/2008/04/19/a-note-about-git-commit-messages.html`. Anyone citing "tpope.net" as the source for the 50/72 rule is citing a dead link; cite tbaggery.com instead.
