## CLAIMS

- ESLint requires an explicit "What changes did you make?" section in its PR template and its real merged PRs fill it with causal, before/after prose rather than a diff summary [eslint-21204].
- ESLint PR #21204's body explains a JS semantics edge case (`var`/`let` catch-parameter shadowing) using only runnable code snippets and named concepts (scope, redeclaration), with zero references to ESLint's internal AST/rule-implementation architecture beyond function names it also defines inline [eslint-21204].
- Of the 15 most recently updated eslint/eslint PRs sampled, the two largest non-bot, non-chore bodies (#21204, and the docs PR fixing a dead JSX spec link) both explain *why* a change is needed in plain terms before describing the change, matching ESLint's template requirement [eslint-21204].
- Homebrew/brew's PR template requires contributors to check "Have you explained why you'd like these changes included, not just what they do?" and "have you given step-by-step commands to reproduce the bug?" as tickable, reviewed checklist items [homebrew-23525].
- Homebrew PR #23525 ("Keep one failure from aborting a batch install") explains five distinct behavior changes as five bullet points, each stating the old broken behavior, why it was broken, and the new behavior, using only Homebrew CLI commands (`brew upgrade`, `brew install`) as the technical vocabulary — no Ruby internals beyond one class name (`DownloadQueue`) used descriptively [homebrew-23525].
- Homebrew PR #23525 discloses AI assistance under Homebrew's Responsible-AI-Usage policy: "Claude Opus 5 high with local review and testing," with a checked box affirming the author reviewed the output and will answer questions without AI [homebrew-23525].
- Homebrew PR #23526 ("Record startup phases in `brew prof --timings`") explains a profiling change using concrete measured numbers ("hiding ~130ms of a ~260ms warm no-op install") rather than abstract claims of improvement [homebrew-23526].
- Of 30 sampled Homebrew/brew merged PRs, roughly half had substantive (>300 char) bodies; the rest were single-line "Fixes #NNNN" or dependency-bot bodies — substantive PRs were not rare outliers but a large fraction of the recent sample.
- Of 60 sampled prettier/prettier merged PR bodies, only 2 filled in the "## Description" field of the template with more than a placeholder comment; 9 of 11 examined in detail left the description section as the unfilled HTML comment `<!-- Please provide a brief summary of your changes -->` [prettier-sample].
- The two Prettier PRs with real descriptions found in the sample ("Switch `json5` to `@bybrave/json5`" and a MegaLinter docs addition) were both minimal one-line links to external context, not causal explanations of a fix [prettier-sample].
- VS Code's live commit stream (30 most recent commits to microsoft/vscode as of 2026-08-14) is heavily authored or co-authored by "Copilot" (GitHub's coding agent), with commit trailers like `Co-authored-by: Copilot <223556219+Copilot@users.noreply.github.com>` and `Copilot-Session: <uuid>` appearing on a majority of sampled commits [vscode-copilot-authored].
- VS Code PR #330910 ("agentHost: anchor the side chat boundary to the inherited turn id") is explicitly labeled "(Commit message generated by Copilot)" in its own body, despite being one of the clearest-written examples found in the sample [vscode-330910].
- VS Code PR #330923 ("Guard RPC proxies against becoming thenables") explains a JavaScript `Proxy`/`await`/thenable deadlock using only standard JS/Promise vocabulary, a runnable example, and a table mapping each affected proxy to its concrete consequence, without requiring familiarity with VS Code's IPC or extension-host architecture beyond the proxy names it defines in the same table [vscode-330923].
- The majority of VS Code PR bodies sampled outside #330923 (e.g. #330756, #330759, #330737, #328461, #327290) require pre-existing familiarity with VS Code-specific and product-specific concepts not defined in the PR body itself — "Agent Host," "Copilot SKU," "ADR 004," "managed settings service," "CAPI proxy" — to follow the causal argument [vscode-copilot-authored].

## SYNTHESIS

Two of five candidate categories produced genuinely strong, verifiable outsider-clear examples; two produced a clear negative finding; the individual-writer angle (Julia Evans) and the "friendliest commit messages" search angle were not pursued because the two direct-repo comparisons already returned enough signal to answer the question honestly, and time was better spent verifying real PRs than chasing an unconfirmed blog-vs-commits distinction.

**ESLint and Homebrew/brew are the real finds.** Both have PR templates that *structurally force* a why-before-what explanation ("What changes did you make? Give an overview," "Have you explained why you'd like these changes included, not just what they do?"), and — unlike Prettier's identical-looking template — contributors actually fill them in with prose, not just check boxes. Critically, the prose in the best examples (ESLint #21204, Homebrew #23525) is legible to a competent generalist: ESLint's explanation of the `var`/`let` catch-shadowing bug needs only JS scoping knowledge, not ESLint's internal rule-fixer architecture; Homebrew's batch-install fix needs only familiarity with `brew install`/`brew upgrade` as commands, not Ruby-level formula internals. This is a materially different craft target than the Linux-kernel cluster documented in the prior entry — it's "clear to a daily user of the tool," not "precise for a peer maintainer of the tool's internals" — and both projects hit it consistently, not as isolated outliers. Roughly half of sampled Homebrew PRs and a strong fraction of ESLint's non-bot PRs had this quality; it reads as cultural, template-enforced, not luck.

**Prettier is a negative finding, stated plainly.** Prettier ships the same style of contributor template as ESLint (checkboxes, a Description field, an AI-disclosure checkbox) but the community does not fill it in: 9 of 11 examined non-trivial merged PRs left "## Description" as the literal unfilled placeholder comment. Having a good template is not sufficient — ESLint and Homebrew's discipline is doing the real work, and it's plausible that's maintainer-enforced at review time (ESLint explicitly lists "What changes did you make?" as a required section with sub-checkboxes for PR type; Prettier's is optional-feeling by contrast) rather than emerging from community friendliness alone.

**VS Code needs a stronger caveat than the others.** The user's own framing anticipated this and it holds: the artifact that's genuinely well-written for end users — code.visualstudio.com/updates monthly release notes — is written by a separate, dedicated technical-writing process, not the same channel as the PR/commit bodies. The PR/commit bodies themselves, sampled live from the current main branch, split two ways. A real minority (best example: #330923, the Proxy/thenable guard, which needs only standard JS Promise vocabulary) are genuinely outsider-clear and well-argued. The majority require pre-existing familiarity with VS Code-internal, often extremely recent and feature-branch-specific vocabulary — "Agent Host," "Copilot SKU," "ADR 004," "CAPI proxy," "managed settings service" — that the PR body does not define, so a generalist reader without VS Code's current internal roadmap in their head cannot follow the causal argument even though the prose itself is fluent and well-organized. On top of that, an unanticipated finding: a majority of the most recent live commits to microsoft/vscode are authored or co-authored by GitHub's own Copilot coding agent (visible via `Co-authored-by: Copilot` trailers and `Copilot-Session` UUIDs), and even the single best human-clarity example found in the PR sample, #330910, is self-labeled "(Commit message generated by Copilot)." This means VS Code's current PR/commit corpus is not a clean test of *human* outsider-writing craft at all — it's increasingly a test of what an AI agent, working inside a specialist codebase, chooses to explain and to whom. That's a genuinely different and newer phenomenon than "friendly community writes clear PRs," and conflating the two would overstate the finding.

**Bottom line for the corpus:** if the target is "excellent PR/commit writing for a non-specialist-but-competent reader," ESLint and Homebrew are the strongest verified precedents found so far — stronger than VS Code, and much stronger than Prettier, whose reputation for approachability (real, in its docs and error messages) does not extend to its own PR-writing culture.
