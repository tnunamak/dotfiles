## ANSWER

Topology (C) splits cleanly into two independent legs, and every mature precedent studied here treats them as two *different* protocol problems, not one: the downstream leg (client-to-personal-server) is a normal OAuth/UMA/GNAP authorization-server-to-client relationship where the personal server issues its own tokens under its own trust domain; the upstream leg (personal-server-to-platform) is a second, separate credential the personal server must independently hold or obtain to call the platform's API on the owner's behalf — the two legs should never share a token, and no precedent studied lets them.

For the upstream leg, the right shape is OAuth 2.0 Token Exchange (RFC 8693) delegation, not owner-credential impersonation: the personal server should be an OAuth client to the platform's own AS, exchanging (or minting) a token that carries an explicit actor claim identifying the personal server as *acting for* the owner rather than *being* the owner — RFC 8693 draws this exact line ("with delegation semantics, principal A still has its own identity separate from B... any actions taken are being taken by A representing B" vs. impersonation where "A is given all the rights that B has... and is indistinguishable from B") and the delegation form is what produces the properties PDPP needs: an audit trail (the platform's logs show requests came from the personal server acting for the owner, not from the owner's own session), independent revocability (the platform can revoke the personal server's delegated grant without touching the owner's primary credential), and no exposure of the owner's actual password/session to a third operator.

Owner-credential impersonation is the pattern UK Open Banking explicitly regulated away from — it is literally named "screen scraping" / credential sharing in the Open Banking literature, and PSD2's whole reason for mandating dedicated interfaces (Read/Write APIs, the ASPSP obligation) was to kill that model in favor of token-based, ASPSP-mediated consent; Plaid's own architecture confirms the same lesson from the private sector — Plaid tries hard to route through bank-side OAuth wherever the bank supports it, and only falls back to holding credentials for non-OAuth banks, treating that fallback explicitly as the worse, legacy case, not the design target.

Practically, three sub-patterns exist for how the personal server gets that delegated upstream credential, and prior art picks between them by how much the platform is willing to build: (a) if the platform runs a real OAuth AS (this is PDPP's data-connector case — B, not C, but the mechanism generalizes), the personal server does a normal OAuth authorization-code flow as a registered client, holding a platform-scoped access/refresh token pair, exactly like Plaid's OAuth-institution flow or Google Actions/Alexa account linking, where "the skill is still considered the client because it's the only component that ever accesses the protected resource" even though the assistant/intermediary orchestrates the UX; (b) if the platform additionally supports RFC 8693 token exchange, the personal server can request a narrower, audience-restricted, actor-tagged token specifically scoped to the resource it needs to fetch on this call, which is strictly better for auditability than a long-lived static OAuth token, but very few consumer platforms implement 8693 today, so this is closer to a forward-looking profile decision than a near-term requirement; (c) UMA 2.0's federated-authorization model is the closest fit to (C)'s exact shape (personal server as AS, platform's API as RS) but it assumes the RS-operator (platform) is *willing to register with and trust* an external, per-user AS via a Protection API Access Token (PAT) — a "the RS as an OAuth client obtains a PAT from the AS" cooperation step no consumer platform studied here (Amazon, Google, etc.) has ever agreed to do, which is precisely the adoption failure this corpus's UMA/Solid entry already documents; PDPP's actual leverage today is closer to Plaid's than UMA's — a client-side integration the platform tolerates or partners on, not a protocol the platform natively speaks.

What each standard actually contributes to (C), stripped to the load-bearing part: RFC 8693 supplies the *token vocabulary* for delegation (subject_token/actor_token parameters, the `act` claim for chaining, `may_act` for pre-authorizing who can request delegation) but says nothing about discovery, registration, or consent UX — it is a wire format, not an architecture. GNAP (RFC 9635) supplies a cleaner architectural separation of AS and RS as first-class distinct roles and a different client-identity primitive (proof-of-possession key vs. bearer client_id), but its own RFC explicitly punts RS-AS interoperability details to a separate not-yet-normative companion document (GNAP-RS) and has no delegation-chain/actor-claim equivalent to RFC 8693's `act` claim — so GNAP is a plausible session/continuation layer for the downstream (client-to-personal-server) leg, not a ready-made answer for the upstream leg. UMA 2.0's federated-authorization spec is the only standard that names topology (C)'s exact role split (one personal AS, many independently-operated RSes) and defines the real mechanics — RS registers protected resources at the AS's resource-registration endpoint using a PAT it obtained as an OAuth client, and per-request the RS posts a permission ticket to the AS's permission endpoint, returns it to the requesting client in a 401, and later introspects the resulting RPT — but as this corpus's existing UMA/Solid entry established, UMA never got RS-side (i.e., platform-side) adoption outside pilots, for the same reason PDPP would hit here: it requires the platform to cooperate as a UMA-aware RS, which none do. Solid-OIDC is architecturally the closest *shipped* precedent to (B), not (C) — the pod is simultaneously the RS and (via a same- or third-party OpenID Provider referenced from the WebID profile) the identity/AS layer, i.e., Solid already assumes the personal store IS the resource server, matching PDPP's topology (B) rather than proxying to an external platform RS.

What a minimal core spec should mandate vs. leave to a profile: mandate (i) the two-leg separation itself — a normative statement that the client-facing token and the platform-facing credential MUST be different tokens in different trust domains, closing off the single biggest failure mode below; (ii) delegation semantics (RFC 8693-style subject/actor distinction) rather than impersonation for the upstream leg, as a MUST; (iii) that the personal server MUST NOT forward the client-facing token upstream — this is close to word-for-word what MCP's own gateway guidance now states as the field's most common enterprise mistake ("MCP servers MUST NOT forward an inbound client token to upstream APIs... If the server calls an upstream API, it must obtain a separate token from the upstream authorization server"), which is the single strongest, most directly transferable piece of prior art in this whole research pass because it is describing the identical confused-deputy shape PDPP would create. Leave to a profile: which upstream authentication mechanism is actually available per-platform (OAuth code flow vs. token exchange vs., worst case, a platform-specific API key held by the personal server) — this varies per platform and can't be mandated because most platforms don't yet expose the ideal mechanism; caching/consistency policy for proxied vs. cached data; and the exact consent-UX choreography (single combined consent screen vs. sequential), since UK Open Banking shows a workable two-hop UX exists but it required years of regulatory-standard iteration to get right, not something a core spec should freeze on day one.

The red flags prior art actually warns about, and what to do about each: **double consent** — Open Banking's two-hop flow (PSU consents to the ASPSP, ASPSP issues an authorization token to the TPP, TPP exchanges it for an access token) shows double consent is survivable and in fact *load-bearing* for trust — the fix is not to eliminate the second consent but to make the platform-side consent screen show the *personal server's* identity plainly (same principle CIMD/DCR client-metadata display objects exist for), not hide it behind a generic "third-party app" label. **Token laundering** — this is exactly the confused-deputy/token-passthrough risk MCP gateway guidance flags as the most common production mistake; the fix is RFC 8693's actor claim (so any downstream consumer of a re-issued token can see it was re-issued, by whom, and for whom) plus the strict rule that the client-facing and platform-facing tokens are never the same value. **Cache/consistency** — none of the standards researched (UMA, GNAP, RFC 8693, Solid-OIDC) specify caching policy at all; this is squarely a profile-level decision, and the two real-world analogs (Plaid refreshes on a 6-24h cadence and treats its stored copy as the source of truth between refreshes; a pure proxy-without-cache has no consistency problem but pays a live-roundtrip cost and platform-availability dependency on every read) are the two ends of a spectrum PDPP should pick explicitly per-connector rather than adopt uniformly. **Aggregator liability** — Plaid's public architecture goes out of its way to minimize what it stores (metadata/tokens, not raw credentials, wherever OAuth is available) precisely because liability follows what you hold; a personal server proxying live to the platform (no persistent copy) has structurally less liability exposure than one that collects and stores (topology B) — this is a real, not cosmetic, argument in favor of (C)-as-proxy for platforms/data classes where PDPP does not need offline/historical access, and a real argument for (B) where it does.

## CLAIMS

- RFC 8693 (OAuth 2.0 Token Exchange) Section 1.1 defines the delegation/impersonation split verbatim: impersonation is "when principal A impersonates principal B, A is given all the rights that B has within some defined rights context and is indistinguishable from B in that context"; delegation is "principal A still has its own identity separate from B, and it is explicitly understood that while B may have delegated some of its rights to A, any actions taken are being taken by A representing B." [rfc8693]
- RFC 8693 Section 4.1 defines the `act` (actor) claim to express delegation and identify the acting party; delegation chains nest one `act` claim within another, with the outermost representing the current actor and nested claims representing prior actors; a token consumer applying access-control policy MUST only consider top-level claims and the current actor per the outermost `act` claim. [rfc8693]
- RFC 8693 Section 4.4 defines `may_act`: "makes a statement that one party is authorized to become the actor and act on behalf of another party," letting an AS determine whether a client is authorized to engage in the requested delegation. [rfc8693]
- RFC 8693 Section 2.1 defines the exchange request parameters: `subject_token` (REQUIRED) "represents the identity of the party on behalf of whom the request is being made"; `actor_token` (OPTIONAL) "represents the identity of the acting party... typically the party that is authorized to use the requested security token and act on behalf of the subject." [rfc8693]
- RFC 9635 (GNAP) Section 1.2 defines AS and RS as separate roles ("Authorization Server: server that grants delegated privileges... in the form of access tokens"; "Resource Server: server that provides an API on protected resources, where operations require a valid access token issued by a trusted AS") but Section 1.2/1.3 explicitly punts RS-AS interoperability mechanics to a separate, not-covered companion document: "The means for an authorization server and resource server to interoperate are discussed in [GNAP-RS]." [rfc9635]
- GNAP's continuation mechanism (RFC 9635 Section 3.1/Section 5) lets a client continue/modify an existing grant request via a continuation access token bound to the client instance's key, but the RFC has no delegation-chain or actor/subject-claim mechanism analogous to RFC 8693's `act` claim — multi-hop delegation of the RFC 8693 kind is out of scope for the core GNAP spec. [rfc9635]
- UMA 2.0 Federated Authorization for UMA 2.0 (docs.kantarainitiative.org, oauth-uma-federated-authz-2.0) Section 3.2 defines the RS-to-AS resource-registration API (POST/GET/PUT/DELETE at the AS's `resource_registration_endpoint`), gated by a Protection API Access Token (PAT) the RS holds as an OAuth client of the AS. [uma-fedauthz]
- UMA federated-authz Section 1.3: "A PAT is unique to a resource owner, resource server used for resource management, and authorization server used for protecting those resources. The issuance of the PAT represents the authorization of the resource owner for the resource server to use the authorization server for protecting those resources" — i.e., the resource OWNER must separately authorize the specific RS-AS pairing before any resource registration can occur. [uma-fedauthz]
- UMA federated-authz Section 4: when an unauthenticated/under-scoped client requests a protected resource, the RS posts to the AS's `permission_endpoint` to obtain a permission ticket (HTTP 201, single ticket), then returns it to the client in a 401 response along with the AS's location; the client then negotiates with the AS directly to obtain an RPT (requesting party token) using that ticket. [uma-fedauthz]
- UMA federated-authz Section 5.1: the RS validates the RPT either via token introspection at the AS (posting the RPT with the PAT in the Authorization header, receiving `active` plus a `permissions` array of granted `resource_id`/`resource_scopes`), a cached introspection response, or local self-contained validation. [uma-fedauthz]
- Solid-OIDC treats the pod as the Resource Server and a (potentially separate) OpenID Provider referenced from the user's WebID profile document as the Authorization/Identity layer; authentication method is decoupled from the WebID/authorization wrapper (any OIDC-compatible IdP can back a WebID). This matches PDPP topology (B) — personal store as its own RS — not topology (C)'s proxy-to-external-platform-RS shape. [solidoidc-primer]
- A 2026 research direction (arXiv, cited via search, not independently fetched) proposes decoupling Solid's combined data+control resource model further into a distinct LDP-serving Resource Server and a separate Authorization Server using ODRL policies — evidence that even Solid's own community treats today's shipped pod-as-RS-and-AS coupling as a known limitation rather than a deliberately chosen topology-(C)-style split. [csolid-authz]
- Plaid's architecture routes through the bank's own OAuth flow wherever the institution supports it — user authenticates directly with the bank, the bank issues an access token to Plaid, and "credentials never touch Plaid or the app"; only for non-OAuth institutions does Plaid fall back to holding user-entered bank credentials directly, encrypting them, and using them to log in on the user's behalf — a fallback Plaid's own public materials frame as the legacy/worse case, not the design target. [plaid-authn]
- Plaid's tokenized-access model: after Plaid Link, the integrating app receives only an `access_token` (plus `item_id`/`request_id`) scoped to a specific connected "item," never a reusable bank credential; tokens are described as scoped, revocable, and expiring, distinct from the user's actual bank password. [plaid-authn]
- Plaid's newer "Core Exchange" product, built on the Financial Data Exchange (FDX) standard, has the consumer authenticate directly with the bank/Data Provider, which issues a scoped token to Plaid using industry-standard protocols so "credentials stay with the consumer" — Plaid is described in this model as a Data Access Platform (DAP), i.e., a registered OAuth client that manages authorization/consent across multiple downstream apps. This is architecturally close to PDPP topology (C): an intermediary that is an OAuth client to the platform on the user's behalf, not a credential holder. [plaid-coreexchange]
- UK Open Banking / PSD2's AISP flow is a "two-hop" token exchange: the TPP contacts the ASPSP; the ASPSP directly contacts the PSU (account holder) to obtain consent; once consent is granted, the ASPSP issues an authorization token to the TPP (hop 1); the TPP exchanges that authorization token for an access token at the ASPSP (hop 2), which it then uses to call the ASPSP's API for the consented duration. The PISP (payment-initiation) flow mirrors the same two-hop pattern. [openbanking-aisp]
- PSD2/Open Banking explicitly regulated away from "screen scraping" (the TPP holding and directly using the customer's bank login credentials) toward this token-based, ASPSP-mediated consent architecture; TPPs must be registered/authorised (FCA or equivalent NCA) before any token exchange can occur, and consent is recorded at the ASPSP and independently revocable there at any time. [openbanking-aisp]
- Current MCP ecosystem guidance (2026 field-practice sources, not a normative MCP-spec quote) states as a hard rule that "MCP servers MUST NOT forward an inbound client token to upstream APIs... the server must obtain a separate token from the upstream authorization server," calling inbound-token passthrough to an upstream API "the single most common enterprise design failure in MCP deployments observed in the field," and names the resulting risk pattern "confused-deputy" for gateways that act as a single OAuth client to upstream ASes while serving many inbound clients. [mcp-gateway-2026]
- Alexa Skills account linking: the skill is the OAuth client of record even though Alexa itself performs some of the flow steps on the skill's behalf ("Alexa makes requests to the authorization server to get an access token... the skill is still considered the client because it's the only component that ever accesses the protected resource"). Alexa additionally supports a "reciprocal authorization" pattern letting the skill's backend call back into Alexa's own resources, requiring the skill's service to host its own authorization endpoint for that reverse direction. [alexa-linking]
- Google Actions/Assistant account linking: the developer's service hosts an authorization endpoint that Google opens in the user's browser; the user authenticates and consents there, the developer's service issues a token back to Google via redirect; two flow variants exist (OAuth implicit — long-lived access token returned directly; OAuth authorization-code — short-lived code exchanged for access+refresh tokens at a separate token endpoint), with the authorization-code flow recommended whenever token expiration/rotation is needed. [google-linking]
- (Reused from existing corpus entry, not re-derived here) UMA 2.0's core spec explicitly scopes out the resource data model and query API ("any such partitioning by the resource server or owner is outside the scope of this specification"), and an academic analysis notes UMA "does not prescribe any interaction between multiple ASs" for cross-AS federation; UMA was presented to the IETF OAuth WG at IETF 104 (March 2019) but never taken up, and never achieved RS-side (platform-side) multi-vendor adoption outside pilots like HIE of One. [uma-dead-pool]

## SYNTHESIS

The research converges on a single load-bearing distinction that every successful multi-party precedent enforces and every failed/stalled one (UMA's RS-side adoption, Solid's "platform must expose a Pod" requirement) runs aground on: whether the platform being fetched from has to actively cooperate as a protocol-aware party, or merely has to keep running its existing OAuth AS (or, worse, no AS at all) while an external intermediary does the integration work. UMA federated-authz is architecturally the most precise match for PDPP's topology (C) — it literally names "AS operated separately from RS" as its core scenario — but its adoption history (never taken up by IETF, no RS-side multi-vendor traction beyond pilots) is a direct warning: the RS-cooperation requirement (PAT issuance, resource registration, permission-ticket handling) is exactly the ask no consumer platform has agreed to. Plaid and UK Open Banking succeeded at roughly PDPP's topology-(C) shape specifically because they did NOT require the platform/bank to adopt a new protocol — they required only that the platform (a) run a standard OAuth AS (increasingly true, and mandated by regulation for UK banks) and (b) tolerate a registered third-party client. That is a materially lower bar than UMA's, and it is the bar PDPP should design against for near-term platforms, while treating UMA/GNAP-style native RS cooperation as the aspirational, later-stage profile for platforms willing to build it.

The two-leg separation (client-facing token vs. platform-facing token, never shared) is the single most transferable finding, and it is corroborated from three independent angles that don't cite each other: RFC 8693's delegation-vs-impersonation split (a protocol-design argument), PSD2's regulatory rejection of screen-scraping (a regulatory argument), and current MCP-gateway field practice naming inbound-token-forwarding-to-upstream as the most common production security failure (an operational-incident argument). When three unrelated bodies of prior art — a 2020 IETF RFC, 2015-era EU financial regulation, and 2025-2026 MCP production postmortems — converge on the identical shape of failure, that is about as strong a signal as this kind of corpus-first research produces. PDPP's design should treat "never forward the client's token upstream; always mint or exchange a separate, actor-tagged, platform-scoped credential" as a hard architectural invariant for topology (C), not a stylistic preference.

## Addendum 2026-09-02 (session 74b4f237): do precedents forbid using the owner's own session with a platform?

Question from the owner: connectors run on the owner's server with the owner's own credentials (API tokens, app passwords, sometimes a browser session). Does prior art say "never use the user's session; always connect as an identified client"?

- **PSD2 RTS (EU 2018/389), Art. 30(1)(a) and 33(5)** — the objection is to *unidentified* access, not to using the customer interface. Art. 30(1)(a): TPPs must be "able to identify themselves towards the account servicing payment service provider". Art. 33(5), the fallback ("screen scraping plus") when the dedicated API fails: ASPSPs "shall ensure that the payment service providers referred to in Article 30(1) can be identified and can rely on the authentication procedures provided by the account servicing payment service provider to the payment service user." So the regulated model permits driving the customer-facing interface *provided the third party identifies itself*. Source: https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32018R0389
- **Home Assistant ADR-0004 (web scraping)** — "We no longer accept any new integration that relies on webscraping"; existing ones deprecated over 2 releases. Rationale is *engineering*, not legitimacy: "very fragile, break often", IP bans, heavy browser dependencies. Explicitly allowed: custom (non-core) integrations may scrape; extracting fields from login forms during authentication is allowed; user-supplied API tokens/app passwords are the normal path. Source: https://github.com/home-assistant/architecture/blob/master/adr/0004-webscraping.md
- **SMART on FHIR** — no opinion on user sessions: it is provider-native by construction; every app is a registered OAuth client of the EHR.

Reading: the regulated precedent draws the line at *identification of the acting party*, and the self-hosting precedent draws it at *fragility*. Neither says an owner may not use their own account with their own software. The distinct live-proxy concern is amplification and attribution: each third-party client query becomes a platform call under the owner's session on a schedule the owner does not control.
