- [A hard hang with no panic, no oops, no ARP, steady power draw, and no disk activity on non-ECC memory is best explained by memory/IMC corruption disabling the panic path itself — PLUS why kdump/pstore then fail to capture it](kernel-silent-hang-diagnosis/diagnosing-silent-kernel-hangs-no-panic-no-trace.md) — 2026-07-29, updated 2026-07-29 — Escalation ladder for a hard hang that never reaches any panic sysctl: hardlockup/softlockup/buddy detectors all require the CPU to still run kernel code, so a total freeze or SMM-level stall defeats all of them; RHEL's own kdump methodology assumes an external hardware NMI source (BMC/NMI button) this machine lacks; Proxmox's watchdog-mux is unconditionally active regardless of HA and iTCO_wdt is safe to enable on a non-HA cluster as a hardware-backed reset (not diagnostic) path; Proxmox bugzilla #6873 (netconsole+bridge, RESOLVED WONTFIX) confirms single-NIC hosts structurally cannot use netconsole; strongest evidence is a documented case (wada-dev) where memtest86+ bit-flip signatures matched independently-recorded kernel GPF/bad-page-state corruption bit-for-bit. **Follow-up:** a clean, deliberate sysrq panic on this machine also produced no vmcore, no auto-reboot, and no pstore/ramoops data despite kdump reporting "ready" — three independent community reports show this identical symptom (loaded kdump, clean panic banner, then silent hang) and each attributes it to an undersized `crashkernel=` (this machine's 192M is below Debian's own 256M x86_64 example and Red Hat's 512-768M troubleshooting fallback for LVM+driver-heavy systems); `__crash_kexec()` runs ahead of `kernel.panic`'s own reboot logic inside `panic()`, so a stuck/failed kexec transition explains both "no vmcore" and "no reboot" as one root cause; pstore/blk's own maintainer (Kees Cook) confirms "if the block layer is shut down during a panic, pstore_blk won't catch the panic" — directly explaining why this machine's LVM-backed pstore_blk LV registered but captured nothing, and why ramoops (no block-layer dependency) remains the better fallback; USB-serial consoles are confirmed viable for ordinary runtime logging but architecturally cannot capture true panic/early-boot output (unlike a real UART or earlycon=); KASLR/nokaslr and Proxmox/IOMMU-vfio interactions were NOT corroborated as relevant by any source found. Recommends: bump crashkernel to 512M+ and retest before any other change.
